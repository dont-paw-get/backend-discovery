# ADR 0006: 스트리밍 서재 도서 마크다운 규격(### 📚) 분리 및 책 열기 연동 계약

- **상태**: Accepted
- **날짜**: 2026-09-01
- **관련 티켓**: CLIAR-211
- **참여**: 오케스트레이터 및 프론트엔드 연동 도메인

---

## 1. 배경 및 문제점

1. **스트리밍(stream=true) 환경의 헤더 전송 시점 한계**:
   - ADR 0005에서 `X-Library-Books` HTTP 헤더를 통해 서재 도서 구조화 데이터를 전달하도록 설계하였으나, 실시간 스트리밍 대화 시 HTTP 응답 헤더는 **에이전트 도구(`search_my_library`)가 실행되기 전인 스트림 개시 시점(TTFB)**에 이미 브라우저로 전송됨.
   - 따라서 백엔드가 대화 생성 중 뒤늦게 수집한 `library_books`가 스트리밍 헤더에 실리지 못해, 프론트엔드가 순수 텍스트 청크만 수신하게 되는 구조적 문제가 발생함.
2. **도서 카드 UI 렌더링을 위한 마크다운 규격 분리 필요**:
   - 기존 외부 도서 추천(`recommend_books`)은 `### 📖 {제목}` 마크다운 카드를 통해 프론트엔드가 [서재에 등록 ➔] 버튼을 렌더링하고 있음.
   - 내 서재 도서 조회(`search_my_library`) 역시 스트리밍 텍스트 청크 내에서 실시간으로 파싱되어 **[책 열기 ➔]** 카드가 표출되도록 명확하고 일관된 마크다운 규격 분리가 필요함.

---

## 2. 결정 사항

### 2.1 추천 도서와 서재 도서의 마크다운 규격 명확한 분리

| 구분 | 마크다운 헤더/포맷 | 항목 구성 | 프론트엔드 액션 |
| :--- | :--- | :--- | :--- |
| **외부 도서 추천** | `### 📖 {도서 제목}` | `- **저자**: {저자명} ({쪽수}쪽)`<br>`- **추천 이유**: {이유}` | **[서재에 등록 ➔]** 버튼 |
| **내 서재 도서 조회** | `### 📚 {도서 제목}` | `- **저자**: {저자명}`<br>`- **독서 상태**: {독서 상태} ({진행률}%)` | **[책 열기 ➔]** (상세 모달) 버튼 |

### 2.2 오케스트레이터 시스템 프롬프트 지침 업데이트
- `CAT_ORCHESTRATOR_PROMPT`, `STORK_ORCHESTRATOR_PROMPT`의 서재 도서 안내 지침을 업데이트:
  - 서두: 사서의 다정한 1인칭 공감/안내 멘트 (1~2줄)
  - 본문: 조회된 각 서재 도서마다 반드시 `### 📚 {도서 제목}` 마크다운 카드 및 `- **저자**:`, `- **독서 상태**:` 출력
  - 분리 규칙: 도서 추천 서식(`### 📖`)은 서재 조회 응답에 절대 사용하지 않음
  - 마무리: 도서 장르/상황에 맞는 창의적이고 유연한 1~2줄 후속 소통(CTA)

### 2.3 오케스트레이터 Fallback 결합 안전장치 확장
- `OrchestratorService`의 `extract_fallback_text` 결합 조건에서 `has_rec_card = "### 📖" in tool_result`, `has_lib_card = "### 📚" in tool_result`로 서재 카드까지 포괄하도록 확장하여, LLM 응답 누락 시에도 안전하게 마크다운 카드가 표출되도록 보장한다.

---

## 3. 프론트엔드 연동 가이드

1. **마크다운 파서 분기 (`MarkdownRenderer.jsx`)**:
   - `### 📖` 블록을 만나면 ➔ 기존 **[서재에 등록 ➔]** 버튼이 달린 추천 도서 카드로 렌더링.
   - `### 📚` 블록을 만나면 ➔ **[책 열기 ➔]** 버튼이 달린 서재 도서 카드로 렌더링.
2. **[책 열기 ➔] 버튼 동작**:
   - 버튼 클릭 시 파싱된 도서 제목(`title`)을 바탕으로 프론트엔드 서재 상태에서 해당 책을 찾아 서재 상세 모달/화면을 엽니다.

---

## 4. 파급 효과
- **스트리밍 실시간성**: SSE/스트리밍 텍스트가 내려오는 즉시 마크다운 렌더러가 서재 도서 카드를 실시간 렌더링 가능.
- **UI 일관성 및 직관성**: 이모지(`📖` vs `📚`)를 통해 추천 도서(등록 대상)와 내 서재 도서(열람 대상)를 사용자와 프론트엔드 파서 모두 한눈에 명확히 구분 가능.
