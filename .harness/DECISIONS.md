| 2026-08-21 | 벡터DB(pgvector) 기반 자체 벡터 인덱스와 그에 기반한 검색을 backend-discovery에서 전부 폐기한다. **자연어 질의 기반 도서 추천 기능 자체는 폐기가 아니라 재구현이다** — 웹 검색 도구를 사용하는 Strands 에이전트로 대체된다. ~~추천 기능은 별도 레포로 이관한다.~~ **[2026-08-21 후속 결정으로 정정]** 별도 레포 이관은 취소되고 backend-discovery 자체가 추천 에이전트로 재설계된다(위 최신 결정 참고). backend-discovery는 `ChatSessionStore`(Redis 기반 대화 세션 관리)를 계속 사용한다 | S3 Vectors 조사(`.harness/research/2026-08-21-s3-vectors-review.md`) 결과 현재 규모(25만 건)·쿼리 패턴(높은 빈도)·하이브리드 검색 요구사항 모두 S3 Vectors의 최적 조건과 반대 방향이라 전환 이점이 없다고 판단했다. 별개로 Strands Agents SDK 도입 조사(`.harness/research/2026-08-21-strands-agents-poc-design.md`)를 진행하며 "추천 에이전트는 공용, 페르소나는 에이전트별 분리, 향후 날씨/시간대/테마 큐레이션까지 에이전트가 담당"하는 확장 가능한 구조가 필요하다는 목표가 확인됐다. 이때 우리 DB의 벡터 인덱스로 도서를 찾는 대신, 에이전트가 웹 검색 도구로 실시간 조회해 추천하는 방식으로 구현 방식이 바뀌는 것이며, "질문하면 추천해준다"는 기능 자체는 유지된다. 폐기된 코드는 `archive/vector-search-poc/`에 원래 경로 구조를 유지한 채 보관해 참조할 수 있게 했다. |
| 2026-08-21 | `POST /internal/sync-book`(단건 동기 HTTP)은 실시간 갱신·테스트용으로 범위를 좁히고, 대량 초기 적재는 별도 CSV 배치로 처리한다. Basic API 담당자 확인: 하루 최대 5,000건, 총 약 25만 건 규모이며 25만 건 CSV 원본 파일은 이미 전달받은 상태 | 25만 건 규모를 단건 HTTP 호출로 적재하면 요청 수·지연시간·부분 실패 처리 비용이 커진다. CSV 배치는 대량 적재에 적합한 방식이고, 단건 동기 API는 Basic API 쪽에서 개별 도서가 생성/수정될 때의 실시간 반영과 통합 테스트 용도로 남겨둔다. CSV 배치 자체(동시성 제어, 실패 재시도, 멱등성)는 별도 티켓으로 분리한다(`.harness/BACKLOG.md` 참고). **[2026-08-21 후속 결정으로 폐기]** 벡터DB/RAG 기반 카탈로그 검색 자체가 폐기되어 이 결정과 관련 ADR(`docs/api/decisions/0001-internal-sync-contract.md`)도 `archive/vector-search-poc/`로 이동했다. |
| 2026-08-21 | `redis.asyncio.Redis`의 메서드 반환값은 mypy override(`ignore_missing_imports`)가 아니라 `typing.cast`로 명시적으로 처리 | `redis`는 `pgvector`/`testcontainers`/`boto3`와 달리 `py.typed` 마커가 있어 실제로 타입이 분석된다. 다만 redis-py가 동기/비동기 클라이언트를 같은 시그니처로 오버로드해 반환형이 `Awaitable[T] | T`로 애매하게 잡힌다. override로 모듈 전체를 무시하면 실제 타입 에러까지 놓칠 수 있어, 호출부마다 `cast`로 async 반환형만 명시했다. |
