# 0001 — `/internal/sync-book` 계약 범위: 실시간 단건 갱신 전용

- 날짜: 2026-08-21
- 상태: 확정
- 관련 티켓: CLIAR-51

## 결정

`POST /internal/sync-book`은 Basic API가 **개별 도서 하나가 생성/수정될 때** 실시간으로
호출하는 단건 동기 HTTP 엔드포인트다. `book_id` 기준 upsert로 멱등하게 동작하며, 통합
테스트에서 읽기 모델에 데이터를 넣는 용도로도 사용한다.

이 엔드포인트는 **대량 초기 적재 수단이 아니다.** Basic API가 보유한 도서 데이터
(하루 최대 5,000건, 총 약 25만 건 규모)를 이 엔드포인트로 한 건씩 호출해 적재하지
않는다. 25만 건 규모의 초기 적재는 별도 **CSV 배치**로 처리하며, 그 배치 작업의
설계(스트리밍 처리, 동시성 제어, 실패 재시도, 멱등성 확보)는 이 티켓 범위 밖이고
별도 티켓 후보로 `.harness/BACKLOG.md`에 정리되어 있다. 25만 건 CSV 원본 파일은
이미 전달받은 상태다.

## 배경

- Basic API 담당자 확인: 신규/변경 도서 데이터는 하루 최대 5,000건, 총 약 25만 건
  규모다.
- 25만 건을 단건 HTTP 호출로 적재하면 요청 수·왕복 지연시간·부분 실패 처리 비용이
  선형으로 커지고, 이 서비스의 임베딩 클라이언트(Bedrock)에도 짧은 시간에 대량
  요청이 몰려 rate limit 문제를 일으킬 수 있다.
- 반면 개별 도서의 실시간 반영(사용자가 방금 등록한 책이 바로 검색되어야 하는 경우)과
  통합 테스트에서의 데이터 준비에는 단건 동기 API가 더 적합하다.
- 두 요구사항(대량 적재 vs 실시간 갱신)을 하나의 엔드포인트로 해결하려 하면 배치용
  최적화(청크 처리, 재시도 큐 등)와 실시간용 단순성이 서로 충돌한다. 계약을 분리해
  각자에 맞는 방식을 쓰기로 했다.

## 대안 검토

1. **`/internal/sync-book`을 배열 요청(bulk)으로 확장** — 요청 크기 제한, 부분 실패
   응답 형식, 타임아웃 처리 등을 이 엔드포인트가 추가로 책임져야 해 계약이 복잡해진다.
   25만 건 규모에서는 HTTP 요청/응답 자체의 오버헤드(직렬화, 커넥션)도 무시하기
   어렵다. 채택하지 않음.
2. **CSV 배치를 별도 파이프라인으로 분리 (채택)** — 대량 적재는 파일 기반 배치가
   스트리밍 처리, 실패한 행만 격리해 재시도하는 구조에 더 적합하다. 단건 API는
   실시간 갱신·테스트 전용으로 단순하게 유지한다.

## 영향

- `docs/api/openapi.yaml`의 `/internal/sync-book` 설명에 "대량 적재 수단이 아님"을
  명시했다.
- CSV 배치 적재는 `.harness/BACKLOG.md`의 "CSV 배치 도서 데이터 적재" 항목으로
  별도 티켓 후보로 남아 있다. 착수 시 이 ADR을 참조해 두 경로(단건 API/배치)가
  동일한 `BookRepository.upsert` 멱등 로직을 재사용하도록 설계해야 한다.
- 이 결정의 근거와 배경은 `.harness/DECISIONS.md`에도 요약되어 있다.
